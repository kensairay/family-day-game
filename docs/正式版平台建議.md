# 家庭日手機網頁小遊戲｜正式版平台建議

## 一、建議結論

若要支援約 250 人同時使用，最推薦採用：

> **Cloudflare Workers + Durable Objects + D1**

如果未來需要上傳任務照片，再加上 **Cloudflare R2**。

這套架構適合本活動的原因是：

- 參加者使用手機行動網路即可加入
- 不需要下載 App
- 適合限時答題、即時分數與排行榜
- 可以由伺服器統一判定答案與分數
- 支援玩家斷線後重新連線
- 不需要自行維護傳統伺服器
- 250 人對此類低頻率答題遊戲而言，屬於中小型流量

## 二、建議系統架構

```text
手機玩家
   ↓
Cloudflare Static Assets／Workers
   ↓
Durable Object：管理單一遊戲房間的即時狀態
   ↓
D1：玩家、隊伍、題目、答案、分數與活動紀錄
   ↓
R2：任務照片或活動素材（有需要時加入）
```

### 1. Cloudflare Static Assets／Workers

負責提供玩家手機頁面、主持人控制台與管理介面。

HTML、CSS、JavaScript 等靜態檔案可透過 Cloudflare 網路快取提供，減少活動現場的延遲與伺服器負擔。

### 2. Durable Objects

每一場活動或每一個遊戲房間使用一個 Durable Object，集中管理：

- 遊戲目前階段
- 目前題目
- 倒數時間
- 玩家連線狀態
- 玩家答案
- 隊伍分數
- 排行榜

Durable Objects 原生支援 WebSocket，適合處理多人遊戲或即時同步。Cloudflare 官方文件指出，單一 Durable Object 可連接數千名客戶端，且適合用來協調聊天室或多人遊戲中的多個連線。

### 3. D1

用於儲存較需要保留的資料：

- 活動設定
- 題目與選項
- 玩家暱稱
- 隊伍資料
- 答題結果
- 分數紀錄
- 主持人操作紀錄

即時遊戲狀態不必每次都寫入資料庫，可以先由 Durable Object 管理，關鍵事件再寫入 D1，降低資料庫負擔。

### 4. R2

只有在任務需要玩家拍照或上傳檔案時才加入，用於儲存：

- 團隊任務照片
- 活動圖片
- 工作人員審核素材

第一版答題遊戲可以先不加入 R2，降低開發複雜度。

## 三、替代方案：Supabase

如果希望開發與資料管理更容易，也可以採用：

- 前端：Cloudflare Pages、Netlify 或 Vercel
- 資料庫：Supabase Postgres
- 即時同步：Supabase Realtime Broadcast
- 在線狀態：Supabase Presence

Supabase 官方支援多人遊戲、即時事件與在線狀態。Broadcast 適合傳送遊戲事件，Presence 適合顯示玩家是否在線。

建議使用方式：

- Broadcast：傳送開始遊戲、切換題目、公布答案、更新排行榜
- Presence：顯示玩家在線人數
- Postgres：儲存玩家、分數、題目與紀錄

不建議使用 Postgres Changes 作為主要遊戲同步機制；即時遊戲事件應優先使用 Broadcast。Presence 也不適合高頻率更新，例如每秒傳送一次玩家狀態。

## 四、兩種方案比較

| 項目 | Cloudflare Workers 方案 | Supabase 方案 |
|---|---|---|
| 即時遊戲能力 | 很適合，Durable Objects + WebSocket | 適合，Realtime Broadcast |
| 開發難度 | 中等 | 較低 |
| 後端控制權 | 高，遊戲邏輯可集中管理 | 中高，資料庫與 Realtime 整合方便 |
| 資料管理 | 需要自行設計 D1 結構 | Postgres 管理較完整 |
| 斷線重連 | 需要自行設計 | 需要自行設計，但有 Realtime 基礎 |
| 主持人控制台 | 可自行整合 | 可自行整合 |
| 任務照片 | Cloudflare R2 | Supabase Storage |
| 適合本活動程度 | **最推薦** | **容易開發的替代方案** |

## 五、正式版建議功能

### 玩家端

- 掃 QR Code 加入
- 輸入暱稱或活動參加碼
- 顯示隊伍與目前分數
- 接收題目與倒數
- 送出答案
- 顯示是否成功送出
- 斷線後自動恢復狀態
- 顯示目前回合與排行榜

### 主持人控制台

- 開始或暫停遊戲
- 切換題目
- 設定倒數秒數
- 公布正確答案
- 查看在線人數
- 查看隊伍分數
- 手動補分或扣分
- 跳過題目
- 結束遊戲並公布名次

### 後台資料

- 建立活動房間
- 編輯題目
- 建立隊伍
- 匯入或匯出參加者名單
- 匯出分數與答題紀錄
- 查看主持人操作紀錄

## 六、行動網路環境的設計原則

現場沒有免費 Wi‑Fi，因此應採用低流量設計：

- 題目以文字與小型圖示為主
- 避免自動播放影片
- 圖片壓縮後再提供
- 每次只傳送必要的遊戲狀態
- 不要每秒更新排行榜
- WebSocket 斷線時使用重新連線機制
- 重新連線後由伺服器傳回完整狀態快照
- 答案送出後顯示「已收到」確認
- 所有答案以伺服器收到時間為準
- 不讓手機端自行決定分數

## 七、250 人活動的可靠性設計

### 建議容量

不要只測試 250 人，應以 **300～350 個模擬連線**進行壓力測試，預留：

- 工作人員手機
- 主持人設備
- 重複掃描的玩家
- 斷線後重新加入的連線
- 行動網路同時重新連線造成的尖峰

### 現場備援

- 準備主持人專用行動熱點
- 準備第二台手機或平板作為備援控制台
- QR Code 同時印在海報、桌牌與主持人簡報
- 遊戲開始前提前開放加入
- 預先載入題目與活動設定
- 少數玩家無法連線時，允許同隊共用手機
- 準備紙本題目或主持人口頭備案
- 保留手動補分功能

## 八、正式版開發順序

### 第一階段：核心遊戲

- 將目前 prototype 的題目流程改為伺服器控制
- 加入活動房間
- 加入玩家與隊伍資料
- 加入伺服器端計分

### 第二階段：主持人控制台

- 開始、暫停與結束遊戲
- 題目切換
- 倒數控制
- 排行榜與分數修正

### 第三階段：可靠性

- 斷線重連
- 狀態恢復
- 重複提交答案防護
- 活動紀錄與錯誤記錄

### 第四階段：任務功能

- 任務闖關
- 驗證碼
- 照片上傳
- 工作人員審核

### 第五階段：壓力測試與彩排

- 300～350 人模擬連線
- 不同手機瀏覽器測試
- 行動網路切換測試
- 主持人完整彩排
- 現場備援流程演練

## 九、最終建議

若由本專案直接進入正式開發，我會採用：

> **Cloudflare Workers + Durable Objects + D1**

具體分工如下：

- Workers Static Assets：玩家頁面與主持人頁面
- Worker API：加入房間、送出答案、讀取狀態
- Durable Object：即時房間狀態、WebSocket、倒數與計分
- D1：題目、玩家、隊伍、分數與活動紀錄
- R2：只有需要照片任務時才加入

正式活動建議使用 Cloudflare Workers Paid，而不是完全依賴免費方案，以保留請求量與活動尖峰的安全空間。
